## Behaviour

### Building recommendations

The owner opens a business report, runs an investigation if needed, then selects **Build
recommendations**. The server reads the selected or latest investigation, the latest opportunity
and the business record. Missing or unsupported evidence returns a reason instead of a generic
recommendation.

Recommendations are idempotent for the same investigation and solution type through the dedupe
key. Existing accepted or dismissed recommendations are not overwritten by a rebuild.

### Reviewing recommendations

Each card shows:

- solution type and hypothesis/evidence-backed label
- confidence and current status
- summary and why it was recommended
- evidence with kind, label, source and date
- grouped must/should/could requirements with acceptance criteria
- accept, dismiss and reset actions

### Prompt generation

Selecting **Generate prompts** sends one AI request for all four platforms. Each returned prompt
is validated independently. Ready prompts are versioned and shown with copy support. Failed
prompts are stored with their quality result and error but excluded from the ready prompt query,
so a failure never appears as a successful prompt.

The prompt panel shows version, provider, model, creation time and quality score. The latest ready
version per platform is displayed. Regenerating creates the next version rather than deleting
earlier prompts.

### Maintenance

A maintenance recommendation can create a real maintenance record. The record starts at
`recommended`. The `/maintenance` workspace supports the full lifecycle, schedule editing and
completion evidence:

- cadence
- next due date
- completed timestamp
- completion note

Completion is blocked without a note of at least five characters. A partial unique index allows
only one non-cancelled record per recommendation.

## Schema

The migration is additive and does not modify existing tables.

### `solution_recommendations`

Stores the interpreted solution, confidence, evidence, requirements, assumptions, unknowns,
source, status and links to business, investigation, opportunity and audit.

### `solution_prompts`

Stores platform prompt versions, quality result, evidence references, provider/model and failure
detail. Ready and failed versions share the table but are separated by status.

### `maintenance_records`

Stores maintenance scope, lifecycle status, cadence, next due date, completion time and completion
evidence.

All three tables have `owner_id = auth.uid()` RLS and service-role grants. The migration first
revokes all inherited `PUBLIC`, `anon` and `authenticated` privileges, then grants authenticated
users only SELECT/INSERT/UPDATE/DELETE. This closes the Supabase default-grant path that otherwise
exposes TRUNCATE outside RLS. The migration ends with `NOTIFY pgrst, 'reload schema'`.

The 2026-11-05 production application created all three tables, columns, indexes, policies, RLS
flags and restricted grants. Verification confirmed there are no anon grants.

## How to use

1. Confirm `supabase/migrations/20261107000000_solution_builder.sql` is applied in production.
2. Open a business and select **View Full Report**.
3. Run or confirm an investigation.
4. Select **Build recommendations**.
5. Review evidence and requirements, then accept or dismiss.
6. Generate the platform prompts and copy the required target.
7. For a maintenance recommendation, create the maintenance record.
8. Open **Maintenance**, set cadence and next due date, then move it through the lifecycle.
9. Add completion evidence before completing.

## Known limitations

- The production schema and application are live, but live AI prompt generation could not be
  exercised from this environment because there is no application session.
- AI prompt language quality depends on the configured provider; the validator only enforces
  structure and safety rules.
- Recommendations are scoped to a specific investigation, so a later investigation can create a
  new recommendation with newer evidence.
- The UI does not show failed prompt history; failed records are retained in the database for
  diagnosis and future admin tooling.
- Production route and asset verification passed. Live report interaction and prompt generation
  remain for an owner-authenticated smoke test.
